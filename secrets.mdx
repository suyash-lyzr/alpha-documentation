A secret is a named value, such as `STRIPE_SECRET_KEY`, that Alpha hands to your session's machine as an environment variable. The agent's commands, the apps it starts and the [Shell](/workspace/shell) read it, and the value never passes through the transcript. If the service has a ready connector, such as Gmail or Notion, sign in under [Integrations](/integrations/overview) instead.

<Warning>
Never paste a key into the composer. Anything you send lands in the transcript and in the agent's context. When your draft holds something shaped like a credential, a warning appears above the composer: "That looks like a Stripe secret key. Keys typed here land in the transcript — add it under Secrets instead, and the agent gets it as an environment variable." It doesn't block sending.
</Warning>

## Global or session: where should a secret live?

A secret lives in one of three places. Most keys belong in **Global**. Use a session secret for a value only one session needs, and a [secret set](#secret-sets) for a list of keys that belongs to one project or one setup.

| | Global secret | Session secret | Secret set |
| --- | --- | --- | --- |
| Reaches | Every session you own | Only the session it was added in | The sessions and setups you attach it to |
| Manage it in | **Account menu → Secrets**, under **Global**, or the **Global** group of any session's **Secrets** tab | That session's **Secrets** tab, in the **This session** group | **Account menu → Secrets**, under **Secret sets** |
| Same name in more than one place | Loses to the others. Its row in a session shows an **overridden** tag ("This session has its own value for it"). | Wins in its own session. | Wins over Global, loses to the session's own secret. |
| Good for | Keys you use everywhere | A test key, or a value that differs per app | The keys one project needs, and setups you share, where each person brings their own keys |
| Removed when | You delete it | You delete it, or delete the session | You delete the set or take a name out of it |

Anything the agent runs can read your secrets, and so can the app it builds. Only add what you'd hand the agent directly.

## Find your secrets

Your secrets are in two places, and both show the same values.

| Where | What it shows |
| --- | --- |
| The **Secrets** page: click your name at the bottom of the sidebar and choose **Secrets** | Everything on your account. The row's badge counts your global secrets. |
| A session's **Secrets** tab: click **+** at the end of the workspace's tab strip and choose **Secrets** | What that one session gets: its own secrets, its secret set and your global secrets. Viewers of a [shared session](/sharing) don't get this tab. |

The **Secrets** page has three sections:

| Section | What it holds |
| --- | --- |
| **Global** | "Environment variables in every session you own.", with **Add secret** at the right. With none yet, it reads "No secrets yet." |
| **Secret sets** | Your own [secret sets](#secret-sets), with **New set** at the right. With none yet, it reads "No sets yet." |
| **From setups shared with you** | The sets of setups other people shared with you, where you fill in your own values. This section appears only when there is one. |

## Add a secret

<Steps>
  <Step title="Open a list of secrets">
    For a global secret, open **Account menu → Secrets**. For a session secret, open the session's **Secrets** tab from the **+** at the end of the workspace's tab strip.
  </Step>
  <Step title="Click Add secret">
    The **Add secret** form opens: "An environment variable for the commands the agent runs, from its next command on."
  </Step>
  <Step title="Fill in Name and Value">
    Type the name your code reads, such as `STRIPE_SECRET_KEY`, and paste the value. **Value** is a single-line field, so a service-account JSON goes in as one line. The eye at its right shows what you pasted.
  </Step>
  <Step title="Choose Available in">
    In a session's tab, the **Available in** switch picks where the secret goes. **This session** is picked first: "Only this session; it wins over a global secret of the same name." **Global** reads "Every session you own." The **Secrets** page skips this choice and always saves globally.

    <Frame caption="From a session, Available in decides where the secret goes, and This session is picked first.">
      <img src="https://cdn.jsdelivr.net/gh/suyash-lyzr/alpha-documentation@d3746aff596b13cbfd84695ae54a27a24310522f/images/secrets/add-secret-form-scope.webp" alt="The Add secret dialog, with a close button at its top right. The description reads An environment variable for the commands the agent runs, from its next command on. The Name field shows the placeholder STRIPE_KEY, and the Value field is empty with an eye button. Under Available in, This session is selected beside Global, with the line Only this session; it wins over a global secret of the same name. Paste a .env instead, Cancel and Add secret sit at the bottom." />
    </Frame>
  </Step>
  <Step title="Save the secret">
    Click **Add secret**. The new row appears in the list. If the name already exists there, the form says "STRIPE_SECRET_KEY is already set there — saving replaces its value." and the button reads **Save**.
  </Step>
</Steps>

New commands see the secret right away, even in running sessions. Anything already running, such as a dev server, keeps its old environment until it restarts. Ask the agent to restart it, or click **Restart shell** in the Shell.

## Import a .env file

1. In the **Add secret** form, click **Paste a .env instead**. The title changes to **Paste a .env**.
2. Paste the file into **.env contents**. Each line holds one `NAME=value`. Blank lines and `#` comments are ignored, `export NAME=value` lines work, and quotes around a value are removed.
3. Tick **Replace values that are already set** if the paste should overwrite names you already have. Left unticked, those names are skipped as "already set".
4. In a session's tab, choose **Available in**, then click **Import**.

<Frame caption="Names you already have are skipped unless you tick Replace values that are already set.">
  <img src="https://cdn.jsdelivr.net/gh/suyash-lyzr/alpha-documentation@d3746aff596b13cbfd84695ae54a27a24310522f/images/secrets/paste-env-import.webp" alt="The Paste a .env dialog. Below it are a Replace values that are already set checkbox, the Available in switch with This session selected beside Global, and Add one instead, Cancel and Import." />

If anything is skipped, the paste stays on screen so you can fix it and import again. **Add one instead** switches back to the single form.

## Copy, replace or delete a secret

Each row shows the secret's name, its masked value and when it last changed, followed by four buttons.

| Action | What it does |
| --- | --- |
| **Copy value** | Copies the value to your clipboard without showing it. |
| **Replace value** (pencil) | Opens **Replace STRIPE_SECRET_KEY** with a **New value** field. It says where the secret applies: "Every session you own gets it." for a global one, "Only this session's sandbox gets it." for a session one. The name can't change; to rename, add a new secret and delete the old one. |
| **Delete** (bin) | Asks "Delete STRIPE_SECRET_KEY? Sandboxes already running keep it until they restart." There is no undo. |
| **Reveal** / **Hide** (eye) | Shows the full value in place. Leaving the page or the tab, or switching sessions, hides it again. |

Values of 12 or more characters show their last four, so you can tell two keys apart without revealing either. Deleting a session secret that shadowed another value brings that value back for the session.

## Secret sets

A secret set is a named list of secret names, such as "Harbor keys" with `STRIPE_SECRET_KEY` and `RESEND_API_KEY`, that you attach to a session or a setup. The set holds the names; each person who uses it keeps their own value for each name. Your values are yours alone: "Your own values. Nobody else sees them."

Use a set when a project needs the same few keys in every session you start for it, or when you share a [setup](/sessions/setups) and everyone who starts from it should bring their own keys rather than use yours.

### Create a set

You can start a set from three places. Each opens the same editor.

| Where | How | What happens on **Save** |
| --- | --- | --- |
| The **Secrets** page | Under **Secret sets**, click **New set**. | The set is created. |
| The composer, on the home screen or in a session | Click **+**, then **Secret set → Create a secret set**. | The set is created and attached to the session you are starting, or to the open session. |
| A setup's form | Under **Secrets & sharing → Secret set**, click **Add keys**. | The set is created, named after the setup, and attached to the setup. |

A new set is called "Set 1", "Set 2" and so on until you rename it.

### Fill in the editor

The editor's title reads **New secret set** for a new set and **Edit Harbor keys** for one of yours.

| Part | What it does |
| --- | --- |
| **Secret set name** | The set's name, up to 60 characters. Two of your sets can't share a name. |
| **Name** column | One secret name per row, such as `OPENAI_API_KEY`. Letters are capitalised as you type, and any other character becomes `_`. |
| **Your value** column | Your value for that name, hidden as you type. The eye shows it. A row that already has a value reads "Saved ••••" and its last four characters; type a new value only to replace it. |
| **Saved** / **Required** | **Saved** means you have a value for the name. **Required** means you don't yet. |
| **×** | Takes the name out of the set. |
| **Add secret** | Adds an empty row. |
| **Paste .env** | Opens a box for pasting a `.env` file into the set. See [Paste a .env into a set](#paste-a-env-into-a-set). Only the set's owner gets it. |
| **Save** | Saves the set's name, its list of names and every value you typed, all at once. It stays dimmed until something changes. |

You can save a set with names but no values, then fill the values in later. Taking a name out of a set also deletes everyone's value for it.

### Paste a .env into a set

For a set you own, you can fill in many names and values at once from a `.env` file.

<Steps>
  <Step title="Click Paste .env">
    At the foot of the editor, click **Paste .env**. A box opens for the file's contents.
  </Step>
  <Step title="Paste the file">
    Each line holds one `NAME=value`. Blank lines and `#` comments are ignored, `export NAME=value` lines work, quotes around a value are removed, and names are capitalised.
  </Step>
  <Step title="Click Add to set">
    A name already in the set takes the pasted value, and new names are added as rows of their own. **Cancel** closes the box without changing anything. If the paste has no line of that shape, the editor says "No NAME=VALUE lines found in that paste."
  </Step>
  <Step title="Click Save">
    Nothing is saved until you click **Save**. Check the rows first, and take out any name the set shouldn't carry with its **×**.
  </Step>
</Steps>

### Attach a set to a session

A session takes one secret set of your own.

- **When you start it:** on the home screen, click **+** and choose **Secret set**, then the set. It shows as a chip in the tray under the composer ("The secret set this session's machine gets"), and its **×** takes it off again.
- **In a running session:** click **+** in the composer and choose **Secret set**, or use the set picker at the top of the session's **Secrets** tab. Pick **None** in the menu, or **No secret set** in the picker, to detach it.

The menu marks the set in use with a check, and a set with missing values shows "2 required" beside its name. A change reaches the session's new commands at once; a running process keeps its old environment until it restarts.

If the session started from a setup that has a set, that set is already attached and isn't offered again. The session can take one more set of its own on top.

### Attach a set to a setup

In a setup's form, under **Secrets & sharing**, the **Secret set** field reads "Sessions from this setup get these secrets. People you share with fill in their own values." Pick one of your sets, or click **Add keys** to create one there. With a set attached, the button reads **Edit keys**, and the set's names are listed under the picker. See [Setups](/sessions/setups).

The setup's build script gets your values too.

### Ask the agent to manage your sets

The agent can make and change your secret sets for you, and attach them to your setups, all by name. It never sees a value and never types one: the values stay yours to add, in the set's editor.

<PromptCard label="Try this">

```text
Make a secret set called "Harbor keys" with STRIPE_SECRET_KEY and RESEND_API_KEY, and attach it to my harbor dev setup.
```

</PromptCard>

Alpha will:

1. Create the set with those two names. Both show **Required** on the **Secrets** page until you add your values.
2. Attach the set to the harbor dev setup, so every session started from it gets those secrets.
3. Tell you to add your values under **Secrets**.

| You can ask the agent to | What happens |
| --- | --- |
| List your sets | It sees each set's names, which of them have a value of yours, and which setups use the set. |
| Create a set | The set gets the names it gives, with no values yet. The [limits for secret sets](#limits-for-secret-sets) apply. |
| Rename a set or change its names | A name it takes out of the set also deletes everyone's value for it, as in the editor. |
| Delete a set | Refused while a setup uses the set, with "setups still use this set (harbor dev) — detach it from each first". Ask it to detach the set from those setups first. |
| Attach a set to one of your setups, or detach it | Sessions started from the setup pick up the change on their next commands. |
| Attach a set when it saves a setup | The set is attached before the setup's build starts, so the build already has your values. If you have no set of that name, the save stops with "no secret set of yours named "Harbor keys"", and nothing is saved. See [Setups](/sessions/setups). |

The agent works only on your own sets and setups. It can't change a set or a setup someone shared with you, and it can't attach a set to a session; do that from the composer's **+** menu or the session's **Secrets** tab.

### Which value wins?

When the same name has a value in more than one place, the session gets the first of these:

1. The session's own secret.
2. The value in the set of the setup the session started from.
3. The value in the session's own set.
4. Your global secret.

The session's **Secrets** tab lists its groups in that order: **This session**, then **Setup's set** and **Set** with each set's name, then **Global**. A row whose value is beaten by one higher up shows an **overridden** tag.

### When a value is missing

A name in an attached set that has no value of yours in the set shows **Required** in the session's **Secrets** tab, and a banner above the groups counts them: "1 required secret has no value." or "2 required secrets have no value." Click **Add it** or **Add them** to open the set's editor and fill them in. Each set row also has its own **Set** button, or **Change** once it has a value.

Until you fill a name in, the session gets your global secret of that name if you have one. Otherwise the name is missing from the session's machine.

### Sets in setups shared with you

When someone shares a setup that has a secret set, you see the set's names but never their values. Sessions you start from that setup use your values.

- On the **Secrets** page, the set is listed under **From setups shared with you**, with a line such as "Shared by Maya Chen – maya.chen@harbor.example for setup harbor dev".
- On the [**Setups**](/sessions/setups) page, the setup's row reads **Add 2 secrets** while yours are missing. Click it to fill them in. Once every name has a value, the button reads **Secrets**.
- The editor shows the set's name, the line "· your own values", and a **Your value** field for each name. Only the set's owner can rename it or change its names.

When the owner changes the set's names, or attaches another set to the setup, sessions started from it pick up the change on their next commands.

### Sets when you publish

A published app gets every name in the session's sets, with the session owner's values, even if you didn't pick those names under **Environment**. A variable you picked under **Environment** wins, then the session's own secret, the set's value and your global secret.

If a name in the set has no value anywhere, the publish stops with "the attached secret set needs RESEND_API_KEY — nothing was deployed". Fill in the value on the **Secrets** page and publish again. See [Publish your app](/publish/publish-your-app).

### Rename, edit or delete a set

On the **Secrets** page, each set's row shows its name, its number of secrets and how many are required. Click the row to list its names, each with its masked value or **Required**. The pencil (**Edit**, or **Your values** for a shared set) opens the editor. The bin (**Delete set**) turns into a **Delete** button; click it to delete the set. There is no undo. Sessions and setups that used the set lose its values from their next command.

### Limits for secret sets

| Limit | What happens |
| --- | --- |
| {secretSetsMax} | Another set is refused with "at most … secret sets". Sets from setups shared with you don't count. |
| {secretSetNames} | The set is refused with "at most … secrets per set". |
| 60 characters for a set's name | "a set name must be at most 60 characters". An empty name is refused with "give the set a name". |
| A name your account already uses for a set | "you already have a set with this name" |
| The same secret name twice in one set | "STRIPE_SECRET_KEY is listed twice" |

Names in a set follow the same [name rules](#name-rules-and-limits) as any other secret. Every limit is also listed in [Limits](/reference/limits#routines-setups-and-secrets).

## What happens when the agent needs a key?

The agent is told never to ask for keys in a message. When its work needs keys you haven't added and no connector covers the service, it asks for all of them in one card, and marks the ones your app can run without as optional. Then it carries on with whatever doesn't need them and finishes its turn. Keys you already have, in this session or globally, aren't asked for again.

### Read the card

The card names each key the agent's code reads. For one key, the agent's reason sits under its name; for several, the card lists their names, such as "STRIPE_SECRET_KEY · RESEND_API_KEY · SENTRY_DSN", and each reason shows beside its field in the form. The card's buttons appear once your lists of secrets have loaded.

| State | The card reads | Buttons |
| --- | --- | --- |
| Keys missing | "The agent needs `STRIPE_SECRET_KEY`", or "The agent needs 3 keys". The count leaves out optional keys. | **Add STRIPE_SECRET_KEY**, or **Add 3 keys**, counting every key still missing, optional ones too |
| Some keys added | The same heading, naming or counting what is left | **Add …** and **Tell the agent to continue** |
| Only optional keys left | "`SENTRY_DSN` is optional", or "2 optional keys are unset" | **Add …**, now outlined, and **Tell the agent to continue** |
| Every key added | "`STRIPE_SECRET_KEY` is added" or "3 keys are added", with a check, and "It is in the agent's environment from its next command." ("They are …" for several) | **Tell the agent to continue**, which reads **Told the agent** once the agent knows |

Viewers of a [shared session](/sharing) see the card without its buttons.

### Add the keys

<Steps>
  <Step title="Click Add">
    Click **Add …** on the card, or **Add** on the row above the composer. One form opens, titled **Add 3 secrets** (**Add secret** for a single key), with a field for each key that is still missing. Each field shows the key's name, an **Optional** mark for a key the app runs without, and the agent's reason for it. The eye at the field's right shows what you typed.
  </Step>
  <Step title="Fill in what you have">
    No field is required. Fill in the keys you have and leave the rest blank. To fill several at once, click **Paste a .env instead** and paste the lines into **.env contents**: the form takes only the keys the agent asked for, and says how many it found, such as "2 of 3 asked keys found; other lines are ignored." **Type each key instead** goes back to the fields.
  </Step>
  <Step title="Click Save & continue">
    The keys you filled in are saved as secrets of this session, and the agent is told in one message which keys are in and which are still missing, for example "I added STRIPE_SECRET_KEY, RESEND_API_KEY under Secrets — they are in your environment now. SENTRY_DSN is not set yet. Continue." The button stays dimmed until at least one field has a value.
  </Step>
</Steps>

If a value is refused, the form stays open. The keys that were saved show "Saved" and can't be edited, and the refused one shows why, such as "value must be at most 8192 bytes". Fix it and click **Save & continue** again; only the keys not yet saved are sent.

Every save tells the agent, so you can add the rest later and it hears about each batch. It's told about each key once, whether that comes from the form, the card's **Tell the agent to continue** or the row above the composer. If you switch to another session before a save finishes, the agent isn't told; come back and click **Tell the agent to continue** on the card.

### Keep track of what is missing

While any key the agent asked for is still missing, optional ones included, a row above the composer keeps the request in view, so it never scrolls away. One row covers every request in the session.

| The row reads | When |
| --- | --- |
| "Add `STRIPE_SECRET_KEY` · the agent asked for it" | One key is asked for and none is added yet |
| "Add 15 keys · the agent asked for them" | Several keys are asked for and none is added yet |
| "14 keys remaining · 1 of 15 added" | Some keys are added and some are still missing |

**Add** opens the form on every key still missing. The row stays after you reload the page, and goes once every key is added. Its **×** ("Dismiss") puts it away until the agent asks for another key.

If you add the keys somewhere else while the row is showing, such as on the **Secrets** page or by [importing a .env](#import-a-env-file) in the session's **Secrets** tab, the row tells the agent for you once the last key of a request is in, in one message. Viewers of a shared session don't see the row.

### What the agent can and can't do with secrets

The agent's own reach is deliberately narrow:

| The agent can | The agent can't |
| --- | --- |
| List the names of this session's secrets and of your global ones | Look up a value in your lists of secrets. It sees names only there. |
| Ask you for one key or several in one card. It asks for the same name at most once every two minutes. | Add or change a global secret, or put a value into a secret set |
| Save a value it generated itself, such as a random `SESSION_SECRET`, as a new session secret | Replace a session secret that is already set |
| Read secrets from its environment, like your app does | Delete a secret. Only you can, from the list. |
| Create, rename, change and delete your secret sets, and attach them to your setups, by name. See [Ask the agent to manage your sets](#ask-the-agent-to-manage-your-sets). | Change a set or setup someone shared with you |

A session secret the agent saves wins over a global one of the same name in that session, as one of yours would.

## How are values hidden in the transcript?

Alpha replaces any secret value of 8 or more characters with `[redacted]` wherever it appears verbatim. That covers your global and session secrets and your values in secret sets, in the transcript, publish and setup logs, session search, and files that viewers of a shared session open. Your GitHub token and your sessions' tools keys are masked the same way.

{/* screenshot to capture: /images/secrets/transcript-redacted.png — The command printed the key, and the transcript shows [redacted] in its place. */}

Ordinary values stay visible, because masking them would only hide everyday text: common words such as `production` or `localhost`, an email address, or a plain web address with no credentials in it. A webhook URL or a database URL with a password stays masked.

<Note>
Masking works only on exact matches. Output that transforms a value, such as base64-encoding it, printing part of it or reversing it, can still expose it. Values under 8 characters are never masked.
</Note>

Published apps don't receive your global or session secrets automatically. When you publish, you pick which ones production gets under **Environment**. The names in an attached secret set are the exception: they go with every publish, as described in [Sets when you publish](#sets-when-you-publish). See [Publish your app](/publish/publish-your-app).

## Name rules and limits

If a save is refused, the form shows one of these messages.

| Rule | Message you see |
| --- | --- |
| Names start with a letter or `_`, then letters, digits and `_`, up to 64 characters | "name must start with a letter or _ and contain only letters, digits and _ (max 64 chars)" |
| A few names are reserved (see below) | "PATH is reserved — setting it would break the sandbox shell", with the name you typed in place of `PATH` |
| A value can't be empty | "value must not be empty" |
| One value is at most 8 KB (default) | "value must be at most 8192 bytes" |
| At most {secretsMax} in one place | "at most {secretsMax}" |
| Values in one place: at most {secretsTotal} | "secrets total would exceed …", followed by the cap in bytes |

A few names are reserved: ones the session's machine depends on, such as `PATH` and `HOME`, and names Alpha uses for its own purposes. Case doesn't matter, so `path` is reserved too. If you pick a reserved name, the form tells you, and you can choose another. Every other name is yours to use.

Your global secrets and each session's own secrets are counted separately. A trailing newline from copy and paste is dropped when the value is saved. Secret sets have [limits of their own](#limits-for-secret-sets). Every limit is also listed in [Limits](/reference/limits#routines-setups-and-secrets).
